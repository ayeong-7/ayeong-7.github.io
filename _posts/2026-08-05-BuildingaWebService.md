# 1. 웹 기초 지식
## 1-1. 웹 기본상식
## Background: Web
### 통신
정보를 전하는 것, 현대에는 전화, 인터넷 등의 통신 수단을 이용하여 과거보다 시간과 공간의 제약을 받지 않고 이뤄짐

### 웹
인터넷을 기반으로 구현된 서비스 중 HTTP를 이용하여 정보를 공유하는 서비스
- 웹 서버(Web Server) : 정보를 제공하는 주체
- 웹 클라이언트(Web Client) : 정보를 받는 이용자

### 웹의 발전과 웹 보안의 중요성
과거(초기) : 웹 서비스에 저장된 문서의 내용을 출력해 이용자에게 제공 --(기술 발전)--> 현재 : 다양한 분야에서 이용자에게 편의를 주는 복잡한 시스템
따라서 웹에서 처리하는 정보 자산들이 많아지면서 개인 정보 등의 민감한 정보를 안전하게 보관하고 처리해야 할 필요성이 증가함 -> 웹을 통한 정보 교환 과정에서 이러한 정보들이 유출되거나 악용되지 않도록 보호하는 웹 보안의 중요성 대두

### 웹 서비스, 프론트엔드와 백엔드 // 웹 리소스는 프론트엔드에 대한 설명
- 프론트엔드(Front-end) : 서비스 구조에서 이용자의 요청을 받는 부분
이용자에게 직접 보여지는 부분으로, 웹 리소스(Web Resource)로 구성됨.
  - 웹 리소스 : 웹에 갖춰진 정보 자산, 고유의 URI(Uniform Resource Identifier)를 가지며, 이를 통해 식별됨.
	- HTML(Hyper Text Markup Language) : 웹 문서의 뼈와 살을 담당, 태그와 속성을 통한 구조화된 문서 작성 지원
	- CSS(Cascading Style Sheets) : 웹 문서의 생김새 지정, 웹 리소스들의 시각화 방법을 기재한 스타일 시트, 글자의 색깔이나 모양, 배경 색상, 이미지의 크기나 위치 등 지정
	- JS(JavaScript) : 웹 문서의 동작 정의, 이용자의 브라우저에서 실행되고, 클라이언트가 실행하는 코드라고 하여 Client-Side Script라고도 부름
	- 그 외 : 문서, 이미지, 동영상, 폰트 등
- 백엔드(Back-end) : 서비스 구조에서 요청을 처리하는 부분

### 웹 클라이언트와 서버의 통신
1. C : 이용자가 브라우저를 이용하여 웹 서버에 접속
2. C : 브라우저는 이용자의 요청을 해석하여 HTTP 형식으로 웹 서버에 리소스를 요청
3. S : HTTP로 전달된 이용자의 요청 해석
4. S : 해석한 이용자의 요청에 따라 적절한 동작 수행(리소스 요청 시 탐색, 복잡한 동작 요구 시 필요한 연산 처리)
5. S : 이용자에게 전달할 리소스를 HTTP 형식으로 이용자에게 전달
6. C : 브라우저는 서버에게 응답받은 HTML, CSS, JS 등의 웹 리소스를 시각화하여 이용자에게 보여줌

## 1-2. Background: HTTP/HTTPS
### 인코딩(Encoding)
컴퓨터의 모든 데이터는 0과 1로 구성됨, 0과 1로 우리의 문자를 표현하는 것도 일종의 약속 덕분인데, 이런 약속을 인코딩 표준이라고 함.(ex. 아스키(ASCII)와 유니코드(Unicode))
- 아스키(ASCII) : 7비트 데이터에 대한 인코딩 표준, 호환성 측면에서 국제 소프트웨어 개발에 부담이 됨
- 유니코드(Unicode) : 모든 언어의 문자를 하나의 표준에 담겠다는 목표로 만들어짐, 한 문자는 최대 32비트로 표현되는데, 32비트로 표현할 수 있는 정보의 가짓수는 2^32개로, 대략 42억 개임. 최근에는 한글, 한자, 히라가나, 가타카나, 알파벳과 같은 문자 외에 각종 이모지(Emoji)들도 포함되고 있음

### 통신 프로토콜
웹 서버에 있는 리소스를 클라이언트가 받아 보려면, 
클라이언트는 웹에게 특정 리소스를 지정하여 제공해달라고 요청(요청, Request) -> 서버는 해당 요청을 이해하고, 대응하는 동작을 통해 클라이언트에게 리소스 반환(응답, Response)
- 프로토콜(Protocol) : 규격화된 상호작용에 적용되는 약속
일상생활의 상호작용은 대부분 관습 또는 에티켓이라는 형태의 느슨한 프로토콜을 따르지만, 컴퓨터와 통신할 때는 비교적 엄격한 프로토콜 사용 필요
이유 : 컴퓨터가 해석의 융통성을 발휘하기 어렵고, 이 과정에서 오히려 오류가 발생 가능성을 높일 수 있음 -> 각 통신 주체가 교환하는 데이터(메시지)를 명확히 해석할 수 있도록 문법(syntax) 포함

### HTTP(Hyper Text Transfer Protocol)
서버와 클라이언트의 교환을 요청(Request)과 응답(Response) 형식으로 정리한 프로토콜(클라이언트가 서버에게 요청하면, 서버가 응답)
웹 서버는 HTTP 서버를 HTTP 서비스 포트(TCP/80 또는 TCP/8080)에 대기시킴 -> 클라이언트가 서비스 포트에 HTTP 요청 전송 -> 해석하여 적절한 응답 반환
- 네트워크 포트(Network Port) : 네트워크에서 서버와 클라이언트가 정보를 교환하는 추상화된 장소
- 서비스 포트(Service Port) : 네트워크 포트 중에서 특정 서비스가 점유하고 있는 포트
포트로 데이터를 교환하는 방식 = 전송 계층(Transport Layer)의 프로토콜(대표적인 방식 : TCP, UDP)  
서비스 포트를 표기할 때는 서비스가 사용하는 전송 계층 프로토콜을 같이 표기하기도 함(TCP로 데이터 전송하려는 서비스에 UDP 클라이언트가 접근하면 데이터 교환 안됨)
포트 개수 : 0 ~ 65535번으로, 총 65536개  
0번 ~ 1023번 포트 = 잘 알려진 포트(Well-known port) 또는 특권 포트(Privileged port) (잘 알려진 포트에 서비스를 실행하려면 관리자 권한 필요)

### HTTP 메시지
HTTP 메시지 : HTTP 요청(클라이언트 전송), HTTP 응답(서버 응답)
HTTP 메시지 = HTTP 헤더(Headers) + HTTP 바디(Body)
- HTTP 헤더(Headers)
각 줄은 CRLF로 구분. 
첫 줄은 시작 줄(Start line), 나머지 줄은 헤더(Header)라고 함, 헤더의 끝 줄은 빈줄로 나타냄. 
필드와 값으로 구성되며 HTTP 메시지 또는 바디의 속성을 나타냄. 
하나의 HTTP 메시지에는 0개 이상의 헤더가 있을 수 있음.
- HTTP 바디(Body)
헤더의 끝을 나타내는 CRLF 뒤 모든 줄, 클라이언트나 서버에게 전송하려는 데이터

*CRLF(Carriage Return Line Feed) : CR(커서를 현재 줄의 맨 앞으로 이동시키는 문자) + LF(커서를 다음 줄로 이동시키는 문자), 주로 텍스트 파일에서 줄 바꿈을 나타내는 데 사용되는 제어 문자열(줄을 종결하기 위해 윈도우 운영체제에서는 CRLF, 유닉스 기반 운영체제에서는 LF 사용)

### HTTP 요청
서버에게 특정 동작을 요구하는 메시지. 서버는 해당 동작이 실현 가능한지, 클라이언트가 그러한 동작을 요청할 권한이 있는지 등을 검토하고, 적절할 때만 이를 처리

- 시작 줄 : 메소드(method) + 요청 대상(Request target) + HTTP 버전(각각 띄어쓰기로 구분)
메소드 : 요청 대상에 대해 서버가 수행하길 바라는 동작. HTTP 표준에 정의된 메소드는 8개(ex. GET, POST 등)
  - GET : 리소스를 가져와달라 요청하는 메소드. 이용자가 브라우저에 웹 서버의 주소를 입력하거나 하이퍼링크를 클릭하면, 새로운 페이지를 랜더링하기 위해 리소스가 필요한데, 브라우저가 GET 요청을 서버에 전송하여 리소스를 받아옴
  - POST : 요청 대상에게 데이터를 보내는 메소드. 전송할 데이터는 보통 HTTP 바디에 포함됨. 로그인할 때 입력하는 ID, 비밀번호, 게시판에 작성하는 글 등이 POST로 서버에 보내짐
  - 이 외 : 요청 URI = 메소드의 대상, HTTP 버전 = 클라이언트가 사용하는 HTTP 프로토콜의 버전

### HTTP 응답
HTTP 요청에 대한 결과를 반환하는 메시지로, 상태 정보(Status : 요청을 수행했는지, 하지 않았는지, 안 했다면 이유는 무엇인지), 클라이언트에게 전송할 리소스가 포함됨
- 시작 줄 : HTTP 버전 + 상태 코드(Status Code) + 처리 사유(Reason Phrase)(각각 띄어쓰기로 구분)
  - HTTP 버전 : 서버에서 사용하는 HTTP 프로토콜의 버전
  - 상태 코드 : 요청에 대한 처리 결과를 세 자릿수로 나타냄(약 40여 개, 첫 자릿수에 따라 5 클래스로 구분됨)
    - 1xx : 요청을 제대로 받았고, 처리가 진행 중
	- 2xx : 요청이 제대로 처리됨(202(OK): 성공)
	- 3xx : 요청을 처리하려면, 클라이언트가 추가 동작을 취해야 함(302(Found): 다른 URL로 갈 것)
	- 4xx : 클라이언트가 잘못된 요청을 보내어 처리에 실패함(400(Bad Request): 요청이 문법에 맞지 않음, 401(Unauthorized): 클라이언트가 요청한 리소스에 대한 인증 실패, 403(Forbidden): 클라이언트가 리소스에 요청할 권한이 없음, 404(Not Found): 리소스가 없음)
	- 5xx : 클라이언트의 요청은 유효하지만, 서버에 에러가 발생하여 처리 실패(500(Internal Server Error): 서버가 요청을 처리하다가 에러 발생, 503(Service Unavailable): 서버가 과부하로 인해 요청 처리 불가)

### HTTPS(HTTP over Secure socket layer)
TLS(Transport Layer Security) 프로토콜을 도입하여 HTTP의 문제점(응답과 요청이 평문이라 가로채기 가능)을 보완 -> TLS가 서버와 클라이언트 사이에 오가는 모든 HTTP 메시지를 암호화하여 중간에 탈취하더라도 해석 불가 -> HTTP 통신이 도청과 변조로부터 보호됨(기본 포트 번호 : 443)


## 1-3. 웹 브라우저
## Background: Web Browser
### 웹 브라우저(Web Browser)
인터넷이라는 글로벌 네트워크 위에 구현되어 정해진 프로토콜을 기반으로 통신. 뛰어난 이용자 경험(UX)을 제공하는 소프트웨어
ex. 이용자가 주소창에 주소를 입력했을 때 웹 브라우저가 하는 기본적인 동작
1. 웹 브라우저의 주소창에 입력된 주소 해석(URL 분석)
2. 주소에 해당하는 주소 탐색(DNS 요청)
3. HTTP를 통해 주소에 요청
4. 주소의 HTTP 응답 수신
5. 리소스 다운로드 및 웹 렌더링(HTML, CSS, Javascript)

### URL(Uniform Resource Locator)
웹에 있는 리소스의 위치를 표현하는 문자열
URL = Scheme + Authority(Userinfo, Host, Port) + Path + Query + Fragment
ex. foo(scheme)://example.com:8042(authority)/over/there(path)?name=ferret(query)#nose(fragment)
- Sheme : 웹 서버와 어떤 프로토콜로 통신할지 나타냄
- Host : Authority의 일부로, 접속할 웹 서버의 주소에 대한 정보를 가지고 있음
- Port : Authority의 일부로, 접속할 웹 서버의 포트에 대한 정보를 가지고 있음
- Path : 접근할 웹 서버의 리소스 경로로 '/'로 구분됨
- Query : 웹 서버에 전달하는 파라미터로 URL에서 '?' 뒤에 위치함
- Fragment : 메인 리소스에 존재하는 서브 리소스를 접근할 때 이를 식별하기 위한 정보를 담고 있음. '#' 문자 뒤에 위치함

### Domain name
Host는 Domain name, IP address의 값을 가질 수 있는데, IP address는 네트워크상에서 통신이 이루어질 때 장치를 식별하기 위해 사용되는 주소로, 사람이 외윅 어렵기 때문에 도메인 이름을 사용함
브라우저는 DNS(Domain Name Server)에 도메인 이름을 질의하고, DNS가 응답한 IP address 사용

### 웹 렌더링(Web rendering)
서버로부터 받은 리소스를 이용자에게 시작화하는 행위. 서버의 응답을 받은 웹 브라우저는 리소스의 타입을 확인하고, 적절한 방식으로 이용자에게 전달
사파리는 웹킷(Webkit), 크롬은 블링크(Blink), 파이어폭스는 개코(Gecko) 엔진을 사용하고, 각각의 엔진에 따라 렌더링 과정과 순서, 속도의 차이는 있지만, HTML을 파싱하고 시각화하여 이용자에게 보여주는 것은 같음


## 1-4. Tools: Browser DevTools
### 개발자 도구(브라우저 열고 F12)
- 요소 검사(Inspect) 및 디바이스 툴바(Device Toolbar)
- 기능을 선택하는 패널
  - **Elements** : 페이지를 구성하는 HTML 검사
  - **Console** : 자바 스크립트를 실행하고 결과 확인 가능
  - **Sources** : HTML, CSS, JS 등 페이지를 구성하는 리소스를 확인하고 디버깅 가능
  - **Network** : 서버와 오가는 데이터 확인 가능
  - Performance
  - Memory
  - **Application** : 쿠키를 포함하여 웹 어플리케이션과 관련된 데이터 확인 가능
  - Security
  - Lighthouse
- 현재 페이지에서 발생한 에러 및 경고 메시지
- 개발자 도구 설정

### 요소 검사
특정 요소의 개괄적인 정보를 파악하고, 이와 관련된 코드를 쉽게 찾을 수 있음

### 디바이스 툴바(Device Toolbar)
현재 브라우저의 화면 비율 및 User-Agent를 원하는 값으로 변경 가능, 이를 이용하여 여러 장치에서 렌더딩되어야 할 화면 비율 점검

# 2. Cookie & Session
## 2-1. Background: Cookie & Session
### 쿠키(Cookie)
웹 서버는 클라이언트를 기억할 수 없음(1. 클라이언트의 IP 주소와 User-Agent는 매범 변경될 수 있는 고유하지 않은 정보, 2. HTTP 프로토콜의 Connectionless(하나의 요청에 하나의 응답을 한 후 연결 종료)와 Stateless(통신이 끝난 후 상태 정보를 저장하지 않음) 특징) -> 쿠키(Key + Value로 이뤄진 일종의 단위)을 이용. 서버가 클라이언트에게 쿠키를 발급하면, 클라이언트는 서버에 요청을 보낼 때마다 쿠키를 같이 전송. 서버는 클라이언트의 요청에 포함된 쿠키를 확인해 클라이언트 구분 가능
- 용도 : 클라이언트의 정보 기록과 상태 정보 표현
- 정보 기록 : 웹 서비스 사용 시 볼 수 있는 '다시 보지 않기' 와 같은 팝업 옵션을 기억하기 위해 쿠키에 해당 정보를 기록하고, 쿠키를 통해 팝업 창 표시 여부 판단. 쿠키는 서버와 통신할 때마다 전송되기 때문에 쿠키가 필요 없는 요청을 보낼 때 리소스 낭비 발생할 수 있음 -> Modern Storage APIs를 통해 데이터를 저장하는 것을 권장
- 상태 정보 : 클라이언트를 식별할 수 있는 값을 쿠키에 저장해 사용


- 쿠키가 없는 통신  
서버는 요청을 보낸 클라이언트가 누군지 알 수 없기 때문에 현재 어떤 클라이언트와 통신하는지 알 수 없음
- 쿠키가 있는 통신  
클라이언트는 서버에 요청을 보낼 때마다 쿠키를 포함하고, 서버는 해당 쿠키를 통해 클라이언트를 식별
- 쿠키 변조  
악의적인 클라이언트는 쿠키 정보를 변조해 서버에 요청할 수 있음. 만약 서버가 별다른 검증 없이 쿠키를 통해 이용자의 인증 정보를 식별한다면 공격자가 타 이용자를 사칭해 정보 탈취 가능

### 세션(Session)
인증 정보를 서버에 저장하고 해당 데이터에 접근할 수 있는 키(Session ID, 유추할 수 없는 랜덤한 문자열)를 만들어 클라이언트에 전달하는 방식으로 작동. 쿠키에 인증 상태를 저장하지만 클라이언트가 인증 정보를 변조할 수 없게 하기 위함. 브라우저는 해당 키를 쿠키에 저장하고 이후에 HTTP 요청을 보낼 때 사용. 서버는 요청에 포함된 키에 해당하는 데이터를 가져와 인증 상태 확인

### 쿠키 적용법
쿠키는 클라이언트에 저장되기 때문에 클라이언트는 저장된 쿠키를 조회, 수정, 추가할 수 있음. 클라이언트가 서버에 요청을 보낼 때 저장된 쿠키를 요청 헤더에 넣어 전송하기 때문에 이용자가 요청을 보낼 때 쿠키 헤더 변조할 수 있음 -> 쿠키를 설정할 때, 만료 시간 지정 가능, 만료 시간 이후에는 클라이언트에서 쿠키 삭제(쿠키의 만료는 클라이언트(브라우저)에서 관리됨)

### 쿠키 설정
- 서버 : HTTP 응답 중 헤더에 쿠키 설정 헤더(Set-Cookie)를 추가하면 클라이언트의 브라우저가 쿠키를 설정함
- 클라이언트 : 자바스크립트를 사용해 쿠키 설정

### 쿠키 열람
크롬 Console 활용, 크롬 Application 활용

### 세션 하이재킹(Session Hijacking)
타 이용자의 쿠키를 훔쳐 인증 정보를 획득하는 공격
쿠키에는 세션 정보가 저장되어 있고, 서버는 이를 통해 이용자 식별, 인증 처리를 함. 공격자가 이용자의 쿠키를 훔칠 수 있으면 세션에 해당하는 이용자의 인증 상태를 훔칠 수 있음.

## 2-4. 동일 출처 정책(Same-Origin Policy(SOP))
### Mitigation: Same Origin Policy
이용자가 웹 서비스에 접속할 때, 브라우저는 해당 웹 서비스에서 사용하는 인증 정보인 쿠키를 HTTP 요청에 포함시켜 전달함. 이 특징 때문에 악의적인 페이지가 클라이언트의 권한을 이용해 대상 사이트에 HTTP 요청을 보내고, HTTP 응답 정보를 획득하는 코드를 실행할 수 있음 -> 클라이언트 입장에서는 가져온 데이터를 악의적인 페이지에서 읽을 수 없도록 해야하는데, 이것이 브라우저의 보안 메커니즘인 동일 출처 정책(SOP)임

### SOP의 오리진(Origin) 구분 방법
오리진 = 프로토콜(Protocol, Scheme) + 포트(Port) + 호스트(Host) 
구성요소가 모두 일치해야만 동일한 오리진이라 함.

### Cross Origin 데이터 읽기/쓰기
외부 출처에서 불러온 데이터를 읽으려고 할 때는 오류가 발생해 읽지 못하지만, 데이터를 쓰는 것은 문제 없이 작동함

### 교차 출처 리소스 공유(Cross-Origin Resource Sharing(CORS))
SOP 제한 완화
브라우저가 SOP에 구애 받지 않고 외부 출처에 대한 접근을 허용해주거나 SOP을 완화하여 다른 출처의 데이터를 처리해야하는 경우가 존재함. <img>, <style>, <script> 등의 태그와 특정 포털 사이트에서 운영하는 여러 서비스를 예로 들 수 있음. -> 교차 출처 리소스 공유(CORS) 사용

### CORS
HTTP 헤더에 기반하여 Cross Origin 간에 리소스를 공유하는 방법. 발신측에서 CORS 헤더를 설정해 요청하면, 수신측에서 헤더를 구분해 정해진 규칙에 맞게 데이터를 가져갈 수 있도록 설정
CORS preflight : 수신측에 웹 리소스를 요청해도 되는지 질의하는 과정
- Access-Control-Allow-Origin : 헤더 값에 해당하는 오리진에서 들어오는 요청만 처리
- Access-Control-Allow-Methods : 헤더 값에 해당하는 메소드의 요청만 처리
- Access-Control-Allow-Credentials : 쿠키 사용 여부 판단
- Access-Control-Allow-Headers : 헤더 값에 해당하는 헤더의 사용 가능 여부 나타냄
브라우저는 수신측의 응답이 발신측의 요청과 상응하는지 확인하고, POST 요청을 보내 수신측의 웹 리소스를 요청하는 HTTP 요청을 보냄

### JSON with Padding(JSONP)
'<script>' 태그로 Cross Origin의 데이터를 불러옴. '<script>'태그 내에서는 데이터를 자바스크립트의 코드로 인식하기 때문에 Callback 함수를 활용함

# 3. HTML로 웹 페이지 만드는 방법 익히기

### 배경지식: HTML
HTML(HyperText Markup Language)는 웹 페이지를 구성하는 내용을 정의하고 그 구조를 만드는 데 사용되는 언어. 브라우저가 이를 읽고 해석하여 시각적인 디자인과 콘텐츠로 화면에 보여주는 원리가 숨어 있음.
브라우저와 웹 서버의 통신
1. 브라우저는 웹을 운영하는 웹 서버에 네트워크를 통해 HTTP 요청을 보냄
2. 웹 서버는 브라우저에게 웹 페이지 반환

### HTML 문법
요소(Element)들로 이루어져 있고, 이 요소들을 어떤 규칙으로 작성해야 하는지를 문법이라 부름

HTML 요소(HTML Element)
웹 페이지를 구성하는 기본 단위(ex. 웹 페이지에서 보이는 텍스트, 상자, 입력 폼, 버튼, 하이퍼링크, 이미지 등)
HTML 요소 구조
- 태그
  - <태그이름>내용</태그이름>
  - (1) 여는 태그, (2) 내용, (3) 닫는 태그
  - (1) 여는 태그(Start tag) : 소스 코드 상에서 < 와 > 사이에 태그의 이름이 포함된 <태그이름> 형태를 띄며, 한 요소의 시작을 나타냄
  - (2) 내용(Content) : 요소에 들어갈 내용(ex. 텍스트)
  - (3) 닫는 내용(End Tag) : 소스 코드 상에서 </ 와 > 사이에 태그의 이름이 포함된 </태그이름> 형태를 띄며, 요소의 끝을 나타냄
	- 예시  
	- <h1> : 페이지나 섹션의 제목 표시. 내용 텍스트가 크고 굵은 글씨로 표현됨
	- <p> : 문단을 나타냄. 내용 텍스트를 그룹화하여 단락으로 표시. 텍스트를 읽기 쉽고 구조적으로 정리할 때 사용
	- <strong> : 텍스트를 굵음체로 강조할 때 사용
	- <a> : 다른 페이지나 URL로 이동하는 하이퍼링크 만듦
	- <img> : 웹 페이지에 이미지 삽입. 별도의 닫는 태그 필요 없음
	- <button> : 클릭 가능한 버튼 만듦
- 속성(Attribute)
태그에 추가 정보를 제공하거나 특정 동작을 지정하기 위해 사용. 키-값 쌍의 형태로 작성되며, 여는 태그 안에 위치하고, 여러 개의 속성 존재 가능
태그 구조 : <태그이름 키1="값1" 키2="값2" 키3="값3">내용</태그이름>
- 유의해야할 점
	1. 태그는 중첩 순서를 지켜야 한다. : HTML 요소는 서로 중첩될 수 있지만 올바른 순서로 열고 닫아야 함
	2. 속성은 여는 태그 안에 작성된다. 
	3. HTML은 대소문자를 구분하지 않는다. : 소문자로 작성하는 것이 권장됨
	4. 일부 태그는 닫는 태그가 존재하지 않는다. : img, input 등

HTML 기본 문서 구조
```
<!DOCTYPE html>
<html>
<head>
  <title>My First Page</title>
</head>
<body>
  <h1>Welcome to HTML!</h1>
  <p>Hello, World!</p>
</body>
</html>
```
- <!DOCTYPE html> : HTML 문서의 유형을 브라우저에게 알려주는 선언문. HTML 태그가 아니며, 어떤 버전의 HTML을 기준으로 문서를 해석해야 하는지 정보를 제공하는 역할
- <html> : HTML 문서의 시작을 나타냄. 모든 HTML 문서는 <html> 태그를 포함해야 함
- <head> : HTML 문서의 메타데이터(Metadata)를 작성하는 부분. HTML5부터는 생략 가능
*메타데이터 : 데이터에 대한 데이터. 데이터 자체라기 보다는 데이터를 설명하는 데이터
- <body> : HTML 문서의 본문을 정의. 이용자가 웹 페이지에서 직접 볼 수 있고, 모든 HTML 문서는 <body> 태그를 포함해야 함
- <br> : 내용에 개행을 추가. 줄바꿈을 넣는 목적으로 사용됨
- <img> : src 속성을 불러올 이미지 파일의 경로 지정
*<img> 태그를 <a> 태그로 감싸면 이미지에 하이퍼링크를 부여하는 것도 가능


# 4. Flask로 웹 서버 코딩하는 방법 익히기
## 배경지식: Flask
### 웹 서버(Web Server)
요청을 받으면 응답을 돌려주는, 브라우저의 요청을 처리해서 알맞은 웹 페이지를 반환하도록 논리 흐름이 구현된 프로그램

### 웹 서버는 어떻게 만들어질까?
웹 프레임워크(Web Framework)를 사용해서 개발. 웹 프레임워크는 웹 개발을 위해 반복적이거나 기본적으로 필요한 기능과 뼈대를 제공하는 개발 환경. 
- 프레임워크가 없다면?
1. 브라우저와 TCP 소켓 통신을 맺음
2. 소켓으로부터 데이터 받음
3. 받은 데이터가 HTTP 프로토콜 표준에 부합하는 HTTP 요청인지 검사
4. HTTP 요청 메시지에서 어떤 경로의 웹 페이지를 요청하는지 추출
5. 추출된 경로에 맞는 HTML 문서를 파일 I/O로 열음
6. 연 HTML 문서 파일의 내용을 읽어서 메모리에 저장
7. HTTP 프로토콜 표준에 맞게 HTTP 응답 구성
8. 메모리에 저장된 HTML 문서 내용도 HTTP 응답에 포함시킴
9. 구성된 HTTP 응답을 앞서 맺어진 소켓을 통해 브라우저에 전달

### Flask
Python 기반 웹 프레임워크. 
```
from flask import Flask, render_template          # Flask 웹 프레임워크 모듈을 불러옵니다.

app = Flask(__name__)

@app.route('/simple_page')                        # /simple_page 경로로의 요청이 들어오면,
def get_simple_page():                            # get_simple_page()를 실행합니다.
    return render_template('simple_page.html')    # HTML 문서인 simple_page.html을 반환합니다.

if __name__ == '__main__':
    app.run(host='0.0.0.0', port=31337)           # 웹 서버를 구동합니다.
```

### 템플릿 렌더링
서버의 Python 코드에서 생성한 변수나 값을 뼈대인 HTML 코드에 삽입하여 최종 HTML 문서를 만드는 과정
- HTML 템플릿(= HTML 코드) : HTML 문서 파일이지만, 코드 안에 실제 데이터만 채워지기 이전 기본적인 뼈대만 갖춘 상태 HTML 문서
- 최종 HTML 문서 : 실제 데이터가 채워져서 최종적으로 완성된 HTML 문서

### 템플릿 렌더링 기호(Symbol)
- {{ 표현식 }} : 표현식을 실행한 결과 삽입 가능
- {% 구문 %}(조건문) : if 문, if-else 문, if-else if-else 문 사용 가능. {% endif %}로 끝나야 함
- {% 구문 %}(반복문) : for 아이템명 in 순회가능한데이터 : 순회가능한데이터는 순회할 대상이며, 아이템명은 각 반복의 현재 요소임. {% endfor %}로 끝나야 함
- 템플릿 상속 구문
  - 부모 템플릿, 자식 템플릿이 필요
  - {% block 블록명 %} {% endblock %} : 부모 템플릿과 자식 템플릿 모두에서 사용. 부모 템플릿에서는 자식 템플릿에서 덮어쓸 부분을 정의, 자식 템플릿에서는 부모 템플릿에 반영할 데이터 지정 가능
  - {% extends '부모템플릿파일이름' %} : 자식 템플릿에서 사용 가능. 이 구문을 사용하여 부모 템플릿을 상속
  - {# 주석 #} : 최종 결과물에 출력되지 않는 주석이나 참고 정보를 작성할 때 사용. HTML 주석은 브라우저 웹 페이지 화면에만 안 보일 뿐 HTML 소스 코드에는 그대로 노출이 되는 정보

### 이용자로부터 입력받기
URL 경로 매개변수(URL Path Parameter)를 통한 입력 처리  
URL 경로 매개변수 : 데이터를 URL 경로의 일부로 포함시켜 서버에 전달하는 방식

### URL 쿼리 매개변수(URL Query Parameter)를 통한 입력 처리
URL 쿼리 매개변수 : URL의 ? 뒤에 오는 매개변수로 이용자가 데이터를 서버로 전달하는 방식 중 하나. ? 뒤에 오는 것이 매개변수 키(Key), =뒤에 나오는 것이 매개변수 값(Value)임

### <form>태그를 통한 POST 데이터 입력 처리

`<form>`태그 : 이용자가 브라우저에 상에서 데이터를 입력한 후 서버로 전송할 수 있는 양식을 웹 페이지에 만듦. 필요한 속성(action : 입력 값을 전송할 URL을 지정하는 속성, method : 입력 값을 전송할 때 사용하는 HTTP 메시지의 메서드 설정)
`<form>` 입력 요소 태그
- `<input>` : <form> 태그 단독으로는 입력 양식을 만들 수 없으며 <input> 태그를 함께 사용해야 입력 가능한 폼을 만들 수 있음
  - type : text(텍스트 입력받는 폼), number(숫자만 입력받는 폼), password(비밀번호를 입력받는 폼. 입력 값이 *로 표시됨)
  - name : 키 설정. 키-값 쌍 형태로 전달됨
  - id : 입력 폼의 고유 식별자
- <button> : 클릭 가능한 버튼 생성

## 5-1. 배경지식: 데이터베이스
### DBMS(Database Management System)
데이터베이스에 새로운 정보를 기록하거나 기록된 내용을 수정, 삭제하는 역할. 다수의 사람이 동시에 데이터베이스에 접근할 수 있고, 복잡한 요구사항을 만족하는 데이터를 조회할 수 있음
- Relational(관계형) : 행과 열의 집합인 테이블 형식. MySQL, MariaDB, PostgreSQL, SQLite
- Non-Relational(비관계형) : 키-값 형태. MongoDB, CouchDB, Redis

### RDBMS(Relational DBMS)
데이터를 표 형식으로 저장하고 관리하는 데이터베이스 모델.  
행과 열의 집합으로 구성된 테이블의 묶음 형식으로 데이터 관리, 테이블 형식의 데이터를 조작할 수 있는 관계 연산자를 제공해야 함

### SQLite
#### 테이블 생성하기
테이블 : 데이터베이스에서 데이터를 저장하는 기본 단위  
*고유키(Unique Key) : 테이블의 특정 행을 고유하게 식별할 수 있는 필드로 설정하는 것. 고유 키로 설정된 필드에는 중복된 값이 저장될 수 없음

- 데이터 추가하기 : INSERT INTO
INSERT INTO 테이블_이름 (열1, 열2, 열3, ...) VALUES (값1, 값2, 값3, ...);

- 데이터 조회하기 : SELECT
SELECT 열_이름1, 열_이름2, 열_이름3, ... FROM 테이블_이름;

- 데이터 수정하기 : UPDATE
UPDATE 테이블_이름 SET 열_이름1 = 새로운값, 열_이름2 = 새로운값 WHERE 조건;

- 데이터 삭제하기 : DELETE
DELETE FROM 테이블_이름 WHERE 조건;
